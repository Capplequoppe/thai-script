# QA Lead Review: ai-conversation-practice

## Executive Summary

This is a well-structured plan with genuinely good instincts — the seam/parallel-pair/integration-proof shape of phase 1 is right, the three-state discipline is applied deliberately in several places, and the architectural decisions mostly carry real rejected alternatives grounded in measured spike evidence. The QA problems are concentrated in three places: **the browser-to-backend boundary has several whole classes of failure that no test in any phase can catch before task 1.4** (CORS, audio container format, non-2xx responses, request timeouts), **the frontend test environment cannot execute two ACs as written** (`MediaRecorder`/`mediaDevices` are undefined in this repo's jsdom harness, and `useMicRecorder` does not exist on the branch the plan builds from), and **the phase-2 bank/tier data model cannot support the containment assertions its own ACs make**. The GPU/non-GPU split is a sound convention but is misapplied in task 2.2 and under-specified in task 3.1.

Verified against the working tree at `caad2c6` (branch `feat/consonant-class-color-coding`) — every repo claim below was checked, not assumed.

## Plan-Level Findings

### Finding QA-1: No CORS anywhere in the plan; the failure is invisible until the gate task, and the fix is itself a trust-boundary decision
- **Severity**: critical
- **Description**: The frontend is served by Vite on `http://localhost:5173` (`playwright.config.ts:11`) and the backend listens on `http://localhost:8000` (task 1.3). Different ports are different origins, so **every `fetch` from the page is a cross-origin request** and the browser will block it unless FastAPI returns `Access-Control-Allow-Origin`. `POST /conversation/judge` with a JSON body also triggers a CORS preflight `OPTIONS`, which FastAPI will answer `405` without `CORSMiddleware`. Nothing in task 1.1 (which scaffolds the app), 1.2 (which fills it in), or the contract doc mentions CORS.

  The reason this is critical rather than a routine omission is the **test topology**: task 1.2's backend tests use `TestClient` (no browser, no origin checks), task 1.3's adapter tests mock `global fetch` (no browser enforcement), and task 1.3's page tests use a stub port. So the first execution anywhere in the plan that can observe this failure is task 1.4 — the `gate: human` task at the end of the phase. The phase's whole structure exists to catch contract mismatches cheaply; this one is guaranteed to be caught expensively.

  The fix is also not neutral. The natural reflex is `allow_origins=["*"]`, which makes a GPU-backed audio endpoint on the user's machine callable by **any web page the user happens to have open** — a real second route into the backend that the plan README's Trust Boundary Inventory does not consider (see QA-31).
- **Recommendation**: Add CORS to task 1.1's scope — an explicit `CORSMiddleware` with `allow_origins=["http://localhost:5173"]` (not `*`), documented in `docs/conversation-backend-api.md`, plus a test-case asserting an `OPTIONS` preflight on `/conversation/judge` from the dev origin returns the allow-origin header and one from a foreign origin does not. Add a Trust Boundary Inventory row for "inbound HTTP origin".

### Finding QA-3: Task 1.3 AC6 is not executable in this repo's test environment
- **Severity**: major
- **Description**: AC6 requires "clicking record drives `useMicRecorder`'s **real** state machine (idle → recording → stopped)". I probed the actual environment: under `// @vitest-environment jsdom` in this repo, `typeof MediaRecorder === "undefined"` and `typeof navigator.mediaDevices === "undefined"`. `useMicRecorder.start()` calls `navigator.mediaDevices.getUserMedia(...)` inside a try/catch, so in the test environment the hook will deterministically land in `"error"` — never `"recording"`, never `"stopped"`, and `judgeReply` will never be called. AC6's assertion ("the stub was called with a Blob") can never be satisfied.

  `renderWithApp.tsx`'s own module docstring is explicit that it is the place where "environment repairs every page-level render test needs and that no global vitest config provides" live (it already repairs `localStorage`, `Audio`, `HTMLCanvasElement.getContext`). Task 1.3's Description tells the executor to add a stub `ConversationPracticePort` to that file but says nothing about a `MediaRecorder`/`mediaDevices` repair.
- **Recommendation**: Add to task 1.3's Description and `covers` an explicit extension of `renderWithApp.tsx` with a `StubMediaRecorder` + `navigator.mediaDevices.getUserMedia` fake (recording a fixed `Blob`), following the existing `StubAudio`/`createdAudioUrls()` convention so the test asserts on a recorded observable rather than hook internals. Add an AC for it so the harness repair is not discovered mid-implementation.

### Finding QA-4: `verdict: "pass" | "fail"` conflates a learner failure with a system failure — the plan's own three-state rule, violated at the contract level
- **Severity**: major
- **Description**: Task 1.2 AC4 (unparseable judge output) and AC5 (transcription failure) both specify the response be `verdict: "fail"` with distinguishing `feedback_en` text. The distinguishing signal is therefore **English prose only**. Two consequences:

  1. Task 3.3 carries "a running tally (`passed`/`total`)" and its AC4 asserts "a summary naming 3 attempted". A backend hiccup, an unparseable judge response, or a dropped audio frame is recorded as a **learner's wrong answer** in that tally. The learner is told they failed a question the system never judged.
  2. No automated test can assert the distinction robustly, because the only discriminator is free text. AC5's enforcement ("DIFFERENT feedback_en text") is satisfied by any two different strings, including two that are equally unhelpful.

  This is precisely the never-asked / asked-and-empty / asked-and-failed collapse the plan says it is guarding against everywhere else — it just happens to be encoded into the contract's type, so the discipline applied in `ConversationOpeningResult` (task 1.3, where "unavailable" is a real union member) was not applied to the verdict.
- **Recommendation**: Widen the contract in task 1.1 to `verdict: "pass" | "fail" | "unscored"` (or `"no_speech" | "judge_error"` as separate members), so the three states are machine-distinguishable end to end. Update task 1.2 AC4/AC5 to assert the discriminant field, not the prose; update task 3.3's tally AC to assert an `unscored` turn is excluded from `passed/total` rather than counted as a failure.

### Finding QA-5: A non-2xx HTTP response is not a `fetch` rejection — no AC anywhere covers it
- **Severity**: major
- **Description**: Task 1.3 AC3 specifies "fetch rejecting (network error, e.g. backend not running) is caught and … resolve to a typed `{status: "unavailable"}`". `fetch` only rejects on network-level failure. A backend that is running and returns `500`, `422`, `404`, or `501` **resolves normally**. The adapter as specified would then call `response.json()` on the error body and either throw an unhandled parse/shape error or map an error payload into a bogus `{status: "ok"}` result — rendering a `verdict` read off a field that isn't there.

  This is directly reachable in this plan, not hypothetical: task 1.1 ships `501` bodies on both real endpoints; task 1.1 AC4 deliberately makes malformed requests `422`; task 3.1 AC3 introduces a `404` for unknown session ids — and task 3.3 has to render something sane when a session id goes stale mid-session. No AC in 1.3, 2.1, or 3.3 mentions `response.ok`.
- **Recommendation**: Add to task 1.3 an AC: a `500`/`422`/`404` response resolves to `{status: "unavailable"}` (or a distinct `{status: "error"}` member) rather than an `"ok"` result or a thrown exception, with a test case per status class. Update task 3.3 to state which state a `404` on a stale session id renders.

### Finding QA-6: No request timeout — "never hangs" is only proven for connection-refused
- **Severity**: major
- **Description**: Task 1.3 AC4 and task 1.4 AC4 both promise the page shows "backend not running" "rather than hanging past a bounded timeout". Both test the same scenario: **nothing listening on the port**, which fails fast at the TCP layer. Neither covers the scenario that is far more likely in this specific system: the backend process is up and accepting connections but the response never comes — models still loading in `lifespan` (CONTEXT.md notes multi-minute cold loads), a GPU OOM stalling generation, or a Whisper call on a long recording. `fetch` has no default timeout; that request hangs forever and the page's spinner hangs with it. Nothing in the plan specifies an `AbortController` or a deadline anywhere in `HttpConversationPracticeClient`.
- **Recommendation**: Add a per-call timeout (`AbortController` + a named constant, generous enough for a warm judge round trip) to task 1.3's Description, with an AC: a request that never resolves within the timeout produces the same `unavailable` state, proven with a fetch stub that returns a never-settling promise. This is cheap and non-GPU. The phase-1 `/health` polling in task 1.4 AC1 should use the same deadline discipline.

### Finding QA-7: Audio container mismatch — the contract says WAV, the browser produces webm/opus
- **Severity**: major
- **Description**: Task 1.1's contract specifies `reply_audio_base64` as "the learner's recorded reply, same base64-WAV shape". Task 1.3 says the adapter "encodes the recorded reply `Blob` to base64" — with no transcoding step. But `useMicRecorder` (verified in the worktree source) constructs `new MediaRecorder(stream)` with no `mimeType` option and builds the blob with `{type: recorder.mimeType}`; in Chromium that is `audio/webm;codecs=opus`. The frontend will therefore send opus-in-webm against a contract that says WAV, and task 1.2's GPU-marked judge tests feed it hand-recorded **WAV** fixtures, so the backend is only ever proven against a format the frontend never sends.

  Whether `faster-whisper` copes depends entirely on whether the backend decodes via PyAV/ffmpeg or via the stdlib `wave` module — and task 1.2 AC2 explicitly reaches for `wave` for the *outbound* audio, which suggests the stdlib path is the executor's default instinct. Task 1.4 is again the first place this can surface, and its fixtures are WAV files injected by `--use-file-for-fake-audio-capture`, which Chromium re-encodes through the same `MediaRecorder` path — so 1.4 would catch it, at the most expensive possible moment.
- **Recommendation**: Decide the wire format in task 1.1 and name it in the contract: either rename the field to `reply_audio_base64` with an explicit `reply_audio_mime` companion and require the backend to decode via PyAV/ffmpeg, or require the frontend to transcode to WAV (16 kHz mono PCM) before sending. Add a task 1.2 non-GPU AC that a webm/opus payload reaches the decoder path without error, and make at least one task 1.2 fixture the actual container the browser emits.

### Finding QA-8: Adding the GPU backend to the shared `playwright.config.ts` makes every existing e2e spec depend on a GPU model load, and `fullyParallel: true` aims N workers at a single-process synchronous backend
- **Severity**: major
- **Description**: Task 1.4 instructs "add a second `webServer` entry to `playwright.config.ts`". Playwright starts **every** `webServer` entry before **any** test in the run, regardless of which spec file was selected. The repo has two existing specs (`e2e/home.spec.ts`, `e2e/lesson-intro.spec.ts`) that have nothing to do with this feature; after task 1.4 they cannot run without booting uvicorn and loading three GPU models. Conversely `npm run test:e2e -- conversation-practice` (task 1.4's own `verify`) does not scope the server start either.

  Separately, the existing config is `fullyParallel: true` with `workers: undefined` outside CI — i.e. one worker per CPU core. CONTEXT.md states the backend is deliberately "single-process, single-GPU, **synchronous per request** — no queue, no worker pool". Several workers issuing concurrent judge requests will serialize behind the GPU, and each waits the sum of the others' latencies. With `retries: 0` locally, the first timeout is a red build. This is a textbook flaky-test setup, and it gets worse in phase 3 where each spec does three sequential judge round trips.
- **Recommendation**: Give the conversation specs their own Playwright project (or their own config file) carrying the backend `webServer` and `launchOptions.args` for the fake mic, so the existing specs are untouched — task 1.4's Description already floats "a dedicated project in `playwright.config.ts`" for the launch args; extend the same reasoning to the server. Add `test.describe.configure({ mode: "serial" })` (or `workers: 1` on that project) with a one-line rationale naming the single-GPU constraint.

### Finding QA-9: The e2e learner-state seeding mechanism is never specified, and three ACs depend on it
- **Severity**: major
- **Description**: Task 2.3 AC4 ("two runs with two different known-word fixtures"), task 3.3 AC4 ("a seeded-below-threshold run … a seeded-above-threshold run"), and task 3.2's AC6 route-level gate all require the Playwright spec to install a specific SRS state into the browser before navigation. The app's SRS state lives in `localStorage` (via `StorageCardRepository`/`StorageLearnerStateRepository`), and **no existing e2e spec seeds anything** — both current specs just `page.goto("/thai-script/")` against whatever the browser profile happens to hold.

  So every one of those ACs rests on a mechanism that does not exist and that no task owns: a `page.addInitScript` that writes the exact storage keys and DTO shapes the repositories read, plus fixtures large enough to be *above* 200 learned words for task 3.3. Getting the DTO shape subtly wrong produces a silently-empty learner rather than a test failure, which would make task 3.3's "below threshold → locked" case pass for entirely the wrong reason.
- **Recommendation**: Add a task (or fold into task 2.3, as the first consumer) that builds an `e2e/fixtures/seedLearner.ts` helper writing the real storage keys via `page.addInitScript`, with its own AC asserting a seeded above-threshold state actually renders the unlocked Dashboard tile — so the seeding is proven by an observable before the gate tests depend on it. Note explicitly that the below-threshold case must distinguish "correctly seeded to 120 words" from "seeding silently failed to 0 words".

### Finding QA-10: Task 2.1's query-parameter decision rests on incorrect size arithmetic
- **Severity**: major
- **Description**: Task 2.1's Architectural Decision justifies comma-separated query params by asserting "the app's whole vocabulary is ~5,000 words … even the full set fits well within a URL length limit". The vocabulary file actually holds **5,451 entries** (verified). More importantly, Thai characters are 3 bytes in UTF-8 and **9 bytes once percent-encoded** (`%E0%B8%81` per character). A 4-character Thai word costs ~37 bytes on the wire, not 4. So:

  - a 200-word learner (exactly the phase-3 unlock threshold): ~7.4 KB of request line
  - a 600-word learner (the largest tier the plan generates): ~22 KB
  - the full vocabulary: ~200 KB

  Typical server request-line limits sit in the 8–16 KB range (uvicorn's h11 backend caps incomplete events at 16 KB by default), so the **first learner who can actually use this feature is already near the limit**, and the largest supported tier is over it. Failure mode is a `431`/connection reset from the server before any application code runs — which, per QA-5, the adapter would not translate into a clean `unavailable`. No AC in 2.1 or 2.3 exercises a snapshot larger than a handful of words; AC3 tests the *empty* extreme only.
- **Recommendation**: Either switch `/conversation/opening` to a `POST` with a JSON body (which task 3.1 already does for `/conversation/session/start` — the plan converges there anyway, so this also removes an inconsistency), or send a compact derived signal (a learned-word *count*, or a rank ceiling) instead of the full word list. Whichever is chosen, add an AC covering a realistic 600-word snapshot end to end, and correct the arithmetic in the Architectural Decision.

### Finding QA-11: The bank's data model cannot support task 2.3's containment assertions
- **Severity**: major
- **Description**: Three related problems in the 2.2 → 2.3 handoff:

  1. **The bank carries no word list.** Task 2.2 AC2 fixes the entry shape as `{id, tier, thai, english}`. Task 2.3 AC1 asserts "`select_entry` returns an entry whose **own words** are all within that set". Deriving an entry's own words at runtime requires Thai tokenization (`pythainlp` newmm) — and `pythainlp` appears nowhere in `backend/`'s dependencies (task 1.1 lists fastapi, uvicorn, pytest, ruff, httpx; task 1.2 adds the three model stacks). The test as specified cannot be written against the specified schema.
  2. **The tier → word-set mapping lives nowhere.** `tier` is "a positive integer". Which words tier 3 permits (the top 250 by rank) is knowledge held only in task 2.2's generator script, in a separate `uv` project, under `scripts/`. Task 2.3's "finds the largest tier whose every word is contained in `known_words`" needs that mapping and has no source for it.
  3. **"Largest tier fully covered" assumes the learner's known set is a rank-prefix.** AC2's example — 300 known words selects the tier-250 entry — only holds if those 300 words are exactly the top 300 by rank. Real learners' `getLearnedEntries()` output follows lesson order and SRS graduation, not a clean frequency prefix; a learner with 300 words who is missing one word from the top 250 satisfies **no** tier and falls into AC3's empty-set branch. Nothing in the plan tests a non-prefix known set, and it is the normal case.
- **Recommendation**: Have task 2.2 emit the per-entry token list (`words: string[]`) and a `tiers` header block mapping each tier id to its word set — tokenization already runs in the generator, so this is free there and removes the runtime dependency entirely. Redefine `select_entry` as entry-level containment (`entry.words ⊆ known_words`, prefer the highest tier among the matches) rather than tier-level, which also makes the non-prefix case work correctly. Add an explicit test case for a non-prefix known set of realistic size.

### Finding QA-12: Task 2.3's Architectural Decision contains an unresolved authoring placeholder that AC3's expected behavior depends on
- **Severity**: major
- **Description**: Task 2.3's Architectural Decision section is literally `**[Author: state the actual empty-vocabulary decision made while building this task — smallest-tier fallback vs. an explicit "not enough vocabulary yet" result …]**`. AC3 correspondingly says the behavior is "the smallest tier, or an explicit … response (this task decides which)". From a QA standpoint this is an AC with no expected value: the test case ("the explicit chosen behavior, tested for that behavior specifically") cannot be written or reviewed until implementation time, and the two branches have materially different downstream cost — the second one requires a new frontend state that is in no task's `covers` list. The task's own Description also notes phase 3 "depends on this task existing and making that call".
- **Recommendation**: Resolve it in the plan. Given task 3.2 gates the whole mode at 200 learned words, the smallest-tier fallback is the low-cost choice (the zero-vocabulary path is unreachable once phase 3 ships, and reachable-but-harmless before it). Write the decision and its rejected alternative into the task, and make AC3 assert a single named behavior. If the "not enough vocabulary yet" branch is chosen instead, add the frontend state to task 2.1's or 3.2's `covers` and ACs.

### Finding QA-13: The GPU / non-GPU split is misapplied in task 2.2 and unfunded in task 3.1
- **Severity**: major
- **Description**: CONTEXT.md's convention is sound and task 1.2 applies it well (pipeline functions take models as arguments precisely so the non-GPU cases can pass fakes — a good decision, explicitly reasoned). Two places break it:

  - **Task 2.2 AC4** ("the script run twice … produces byte-identical output") is marked **non-GPU**, but running the generation script twice means running Qwen2.5-7B twice. Its `verify` is `pytest … -m "not gpu"`, so the one command that gates the task cannot execute its own AC4. Same for **AC2**, which asserts on `conversationStarters.json` — a file that only exists after a GPU run has produced it, so the "non-GPU" schema test fails on a clean checkout or on any machine without a GPU.
  - **Task 3.1** marks all four ACs non-GPU. AC1 requires `POST /conversation/session/start` to return `question_audio_base64` — i.e. a TTS synthesis. That needs a fake TTS on `app.state`. Task 1.2's conftest fakes are only *required* by its own AC4/AC5, which are judge-path cases (fake LLM, fake Whisper); nothing in 1.2's ACs obliges the conftest to cover the TTS pipeline. So 3.1's entire non-GPU suite silently depends on task 1.2 having gone beyond its stated ACs.
- **Recommendation**: For 2.2, split determinism from generation: make the seeded/deterministic **candidate-ordering and id-assignment** logic a pure function tested non-GPU, and move the "run the whole script twice" assertion to a GPU-marked case. Move the `conversationStarters.json` schema test into `backend/tests` (or a frontend test next to the data file, matching `sentences.json`'s precedent) where the file is actually consumed, and state what it does when the file is absent. For 3.1, add an explicit AC to task 1.2 requiring `conftest.py` to expose fakes for **all three** models, so 3.1's dependency is funded rather than assumed.

### Finding QA-14: Task 1.4 AC4 is not implementable given task 1.3's stated design
- **Severity**: major
- **Description**: AC4 asks for "stopping the backend process (or pointing the frontend's base URL at a closed port) before navigating". Both options are closed off:
  - The base URL is, per task 1.3's Description, "a module constant (`http://localhost:8000`, per CONTEXT.md — **not user-configurable in this phase**)". There is no runtime seam to repoint it.
  - The backend process is started and owned by Playwright's `webServer`, which lives for the whole run. Killing it inside one test breaks every subsequent test in the same run — and given QA-8's shared-config problem, breaks the other specs too.
- **Recommendation**: Implement AC4 with `page.route("**/localhost:8000/**", route => route.abort("connectionrefused"))` — it produces exactly the `fetch` rejection the adapter's `unavailable` path is built for, needs no process manipulation, and does not require making the base URL configurable. State that in the AC so the executor does not spend the task rediscovering the constraint. (If configurability is wanted anyway, it belongs in task 1.3 with its own AC, not as a side effect of an e2e task.)

### Finding QA-15: `/health`'s single boolean cannot satisfy task 1.4 AC1's failure message
- **Severity**: minor
- **Description**: Task 1.1 fixes the health shape as `{status: "ok", models_loaded: bool}`, and declares "every field name above is final for this phase". Task 1.4 AC1 requires a timeout failure "naming **which model** never became ready". One boolean cannot carry that. As written the executor either violates the frozen contract or silently drops the useful half of AC1.
- **Recommendation**: Either widen the health shape in task 1.1 to `{status, models_loaded: {stt: bool, judge: bool, tts: bool}}` (cheap, and genuinely useful during a multi-minute cold load), or soften AC1 to "a clear failure message reporting the last observed `/health` body and the elapsed wait".

### Finding QA-16: Backend pytest rootdir / import path is unspecified, and the `verify` commands run from the repo root
- **Severity**: minor
- **Description**: Every backend `verify` is of the form `uv run --project backend pytest backend/tests/... -v` — executed from the repo root, against a project rooted at `backend/`. `--project` selects the environment; it does not change the working directory. With the plan's layout (`backend/app/main.py`, `backend/tests/test_health.py`, no `__init__.py` mentioned), pytest's rootdir inference inserts `backend/tests` on `sys.path`, not `backend/`, so `from app.main import app` fails with `ModuleNotFoundError`. The plan's own run instruction (`uvicorn app.main:app` "from `backend/`") implies a different cwd than the `verify` commands use.
- **Recommendation**: Have task 1.1 pin the configuration explicitly — `[tool.pytest.ini_options] pythonpath = ["."]` plus `rootdir`/`testpaths` in `backend/pyproject.toml`, or `--rootdir backend` in the verify commands. Worth stating once in task 1.1, since all five backend verify lines in the plan inherit it.

### Finding QA-17: The `gpu` marker is unowned, and CONTEXT.md's test-templates cover only one of the plan's three test suites
- **Severity**: minor
- **Description**: Three gaps around the GPU convention's plumbing:
  - No task registers the `gpu` marker. Task 1.1 scaffolds `pyproject.toml` but its ACs don't mention pytest configuration; task 1.2 is the first to use `-m "not gpu"`. Unregistered markers produce `PytestUnknownMarkWarning` and fail outright under `--strict-markers`.
  - Task 2.2 lives in a **separate** `uv` project (`scripts/generate-conversation-bank/`) and also uses `-m "not gpu"` — it needs its own marker registration, which no task owns.
  - CONTEXT.md's `test-templates` block maps `backend/**` to `uv run --project backend pytest {file} -k {name} -v` — with no `-m "not gpu"`, so a reviewer re-running a single named backend test can trip a real model load. There is no template for `scripts/generate-conversation-bank/**` or for the Playwright specs, despite both being named in task `verify` lists.
- **Recommendation**: Add marker registration to task 1.1's AC3 (project is lint-clean **and** its pytest config declares its markers) and to task 2.2. Add the two missing template rows and the `-m "not gpu"` guard to CONTEXT.md.

### Finding QA-18: Task 3.1 AC4 asserts a vacuous property
- **Severity**: minor
- **Description**: AC4: "restarting the backend process (**simulated by constructing a fresh session store in the test**) leaves no session reachable by its old id — proves sessions are genuinely in-memory-only … not accidentally persisted to disk." Constructing a fresh `dict` and observing it is empty is true by construction; the test passes identically whether or not a parallel write-to-disk exists. It cannot fail, and therefore proves nothing about the property it names.
- **Recommendation**: Either drop the AC (the in-memory decision is already visible in the code) or make it falsifiable: run a session lifecycle inside a `tmp_path`-scoped cwd and assert no new files were created, which does detect an accidental persistence layer.

### Finding QA-19: Task 3.1 AC3 names an "expired" session id, but no expiry mechanism exists anywhere
- **Severity**: minor
- **Description**: AC3 is "an unknown/**expired** `session_id` … returns 404". Nothing in the task creates sessions with a lifetime — `SessionState` holds an id, a snapshot, and a set of asked ids, and the store is an unbounded `dict` on `app.state`. Either the word is loose (the AC then tests only the unknown-id case, which is fine) or expiry is intended and unimplemented. The unbounded dict is defensible under CONTEXT.md's single-user YAGNI stance, but the AC should not imply otherwise.
- **Recommendation**: Drop "expired" from AC3 and add one line to the task's Architectural Decision stating that sessions are never evicted, with the single-user-local rationale — so a later reader doesn't read AC3 as evidence of a TTL that isn't there.

### Finding QA-20: Nothing makes `/next` idempotent, and task 3.3 calls it from an effect under `StrictMode`
- **Severity**: minor
- **Description**: `src/main.tsx` wraps the app in `<StrictMode>` (verified), which double-invokes effects in development. Task 3.3 AC1 specifies "after a judged reply, the page **automatically** calls `next()`". If that advance is effect-driven, the development build fires it twice; `/next` is a stateful mutation (it consumes a bank entry from the session's not-yet-asked set), so the learner silently skips a question and a small tier exhausts twice as fast. A double-click on the record/continue control has the same effect. FastAPI additionally runs `def` handlers in a threadpool, so two in-flight `/next` calls on one session can both select before either records its id — handing out the same entry twice, which AC1's "never repeating a question already asked" forbids.
- **Recommendation**: Add a task 3.1 AC: two concurrent/duplicate `/next` calls on the same session either return the same question (idempotent within a turn) or two distinct ones, never a repeat of an already-asked entry — and guard the select-then-record step. Add a task 3.3 test case that a double-invoked advance results in exactly one question transition.

### Finding QA-21: Task 2.2 AC1 asserts the filter's own predicate over the filter's own output
- **Severity**: minor
- **Description**: AC1: "every line that survives the compliance filter tokenizes (pythainlp newmm) to zero words outside the tier's word set". The filter *selects* lines by running exactly that tokenize-and-check. The test therefore re-runs the selection predicate over the selection's output and asserts it agrees with itself — it can only fail if the filter is removed entirely. It gives no evidence the filter is correct (a tokenizer misconfiguration that under-segments and produces spurious "known" tokens passes this test cheerfully).
- **Recommendation**: Test the filter as a unit against hand-authored inputs with known verdicts — a candidate containing `คุย` against a tier permitting only `พูด` must be rejected; a clean candidate must be kept. That is non-GPU, fast, and actually falsifiable. Keep the end-to-end "survivors are clean" check as a cheap GPU-marked smoke test if wanted, but it should not be the primary evidence.

### Finding QA-22: `known_grammar_ids` is built, transmitted, and documented, but never consumed by any task in the plan
- **Severity**: minor
- **Description**: Task 2.1 adds `known_grammar_ids` to the port signature, the query string, the contract doc, and AC1. Task 2.3's `select_entry(known_words: set[str])` takes only words. Task 3.1's session start takes "the known-vocabulary snapshot" and its selection delegates to the same `select_entry`. Grammar ids are used by task 3.2's gate — but that reads `grammar.getLearnedCount()` **locally in the browser**, not from anything the backend received. So no code in this plan ever reads the transmitted grammar ids. This is the plan's clearest YAGNI instance, and it inflates the QA-10 payload-size problem for no return.
- **Recommendation**: Drop `known_grammar_ids` from task 2.1 (contract, port, ACs) until a task actually consumes it, or state in 2.1's Architectural Decision which future selection rule needs it and add the consuming AC to 2.3.

### Finding QA-23: The microphone `denied` and `error` states are handled by the hook and by no AC
- **Severity**: minor
- **Description**: `useMicRecorder` deliberately distinguishes `"denied"` from `"error"` — its own docstring says "the two need different UI and only one of them is ever the user's fault". Task 1.3's page ACs cover: backend unavailable (AC4), question loaded (AC5), record → stopped → judge (AC6), verdict rendered (AC7). Nothing covers a learner who denies the microphone permission prompt, or a device that has no microphone. On a first visit this is a common path, and the page as specified would sit in a state with no rendered explanation. It is the same never-asked/denied/failed collapse the plan polices carefully on the backend side.
- **Recommendation**: Add a task 1.3 AC: with the mic fake rejecting with a `NotAllowedError`, the page renders a distinct "microphone access needed" message (different from the backend-unavailable message and from the idle state), and a generic device failure renders a third, different message.

### Finding QA-24: Task 3.3's three-turn e2e needs a tier with ≥3 entries; task 2.2 sets no minimum bank size
- **Severity**: minor
- **Description**: AC4 drives "a real 3-turn session … and sees a summary naming 3 attempted". That requires the seeded learner's matched tier to hold at least three entries that `select_entry` will hand out without repeating. Task 2.2's output size is whatever survives an LLM generation pass through a compliance filter the spike measured at 78–90% first-pass compliance — and it has no AC on entry count per tier at all. A thin tier turns AC4 into an `exhausted: true` at turn 2 and a red e2e run whose root cause lives two tasks and one phase away.
- **Recommendation**: Add a task 2.2 AC: every tier in the shipped bank holds at least N entries (pick N ≥ 8 so phase 3 sessions have headroom), with the generator looping until the threshold is met or failing loudly. Reference it from task 3.3's AC4 so the dependency is visible.

### Finding QA-25: Malformed-but-present base64 and oversized payloads have no coverage
- **Severity**: minor
- **Description**: Task 1.1 AC4 covers a **missing** field only. A request whose `reply_audio_base64` is present but is not valid base64, or is valid base64 of something that isn't audio, satisfies Pydantic's `str` and reaches the decoder — where an unhandled `binascii.Error` or a codec exception becomes the raw `500` that task 1.2 AC4 promises the learner never sees (AC4 only covers the *judge-LLM* parse failure, not the *audio* decode failure). There is also no size bound on the body, though for a single-user local tool that is a robustness rather than a security concern.
- **Recommendation**: Add a task 1.2 non-GPU AC: a present-but-undecodable `reply_audio_base64` returns a clean `400`/`422` (or the `unscored` verdict from QA-4), never a `500` — and pair it with a task 1.3 AC that the frontend renders that response distinctly rather than as a learner failure.

### Finding QA-26: No GPU-marked test exercises real silence, and Whisper's real silence behavior is not "empty text"
- **Severity**: minor
- **Description**: Task 1.2 AC5 frames the case as "an empty or silence-only `reply_audio_base64` (Whisper would transcribe it as empty/near-empty text)" and tests it **non-GPU with a fake Whisper returning an empty string**. That tests the branch, not the premise. Whisper's well-known behavior on silence and low-level noise is to *hallucinate* plausible text rather than return nothing — so against the real model the empty-transcript branch may simply never fire, and a learner who records silence gets a confident "fail" with a judgment of words they never said. The premise is exactly the kind of thing the spike measured for everything else in this plan, and it is unmeasured here.
- **Recommendation**: Keep the non-GPU branch test, and add a GPU-marked case feeding a genuinely silent WAV through `/conversation/judge`, asserting the "couldn't hear anything" outcome. If the real model hallucinates instead, that is a finding worth having before phase 3 builds a tally on top of it — and the fix (`faster-whisper`'s VAD filter / `no_speech_prob` threshold) belongs in task 1.2, which is the task CONTEXT.md already assigns "VAD-triggered single-shot transcription".

### Finding QA-27: Task 3.2's Dashboard ACs will be forced into CSS-class assertions
- **Severity**: minor
- **Description**: AC4/AC5 assert a "QuickActionCard-shaped tile … renders **disabled**" and "the tile is **enabled** and navigates to `/conversation` on click". The real `QuickActionCard` renders a `<Card>` div — no `<button>`, no `role`, no `disabled` attribute, no `aria-disabled`; "disabled" is expressed only as an `opacity-50` class plus a dropped `onClick`. So a behavioral assertion has nowhere to land, and the test will end up asserting on a Tailwind class string — the implementation-coupled shape the plan's own review criteria warn against, and one that breaks on any restyle.
- **Recommendation**: Assert behavior instead: below threshold, clicking the tile does **not** navigate (the route stays put) and the gap message ("120/200 words learned") is visible; above threshold, clicking navigates. Optionally have task 3.2 add `aria-disabled` to `QuickActionCard` — a small, genuinely useful accessibility improvement that also gives the test a semantic hook.

### Finding QA-28: Route paths in the e2e ACs omit the Vite base path
- **Severity**: suggestion
- **Description**: `vite.config.ts` sets `base: "/thai-script/"`, and both existing e2e specs navigate to `/thai-script/`. Task 1.4 AC2 says "navigating to `/conversation`", task 3.2 AC6 "navigating to `/conversation` directly". In Playwright (against `baseURL: http://localhost:5173`) that resolves to `/conversation`, which the dev server does not serve — the router never mounts, and the assertion fails for a reason unrelated to the feature.
- **Recommendation**: Write the e2e paths as `/thai-script/conversation` in the ACs. (The in-app `<Route path="/conversation">` is correct as-is; only the browser-level navigations need the prefix.)

### Finding QA-29: Two factual slips in task 1.1
- **Severity**: suggestion
- **Description**: (a) The Description says `docs/conversation-backend-api.md` is "a new top-level `docs/` file — **this repo has no existing `docs/` directory; create it**". A `docs/` directory exists at the repo root. Harmless in itself, but an executor told a directory doesn't exist may not look inside it. (b) The same paragraph says "**Two** endpoints, matching CONTEXT.md's naming" and then lists three (`/health`, `/conversation/opening`, `/conversation/judge`); AC2 and the test cases both correctly say three.
- **Recommendation**: Correct both; the contract doc is the artifact two parallel tasks read as ground truth, so its preamble should not miscount its own contents.

### Finding QA-30: Task 3.2's unlock-transition moment is specified in prose and covered by no AC
- **Severity**: suggestion
- **Description**: The Description says to use "`LearnableCallout`'s pattern for the 'you just unlocked this' transition moment if a learner crosses the threshold". No AC mentions it, so it is either unbuilt (prose that misleads a later reader) or built-and-untested. Its trigger condition (detecting a *crossing*, which requires remembering a previous count) is also materially more complex than the pure-function gate the rest of the task describes — worth an explicit decision rather than an aside.
- **Recommendation**: Either cut the sentence (YAGNI — the gate works without it) or add an AC naming the observable and stating where the "previously locked" bit is stored.

### Finding QA-31: Trust Boundary Inventory gaps — origin, the `Source` column's framing, the session id, and the bank file
- **Severity**: major
- **Description**: Against check #9, the table is well-written but incomplete in ways that matter for a service listening on a loopback port:

  1. **No row for inbound origin / who may call the backend.** This is the second route that bypasses every other row: once `uvicorn` is listening on `:8000`, *any* page in the user's browser can `fetch` it — the learner's own frontend is not the only client. Combined with QA-1's likely `allow_origins=["*"]` reflex, an arbitrary site could drive the GPU pipeline. The "Backend base URL" row addresses the *outbound* direction only.
  2. **The `Source` column describes intent, not origin.** "Learner's own microphone, via `useMicRecorder`" and "Frontend's own SRS state … sent to the backend per request" describe where the data is *supposed* to come from. At the backend's boundary, the actual origin of every one of these inputs is "any local process or page that can reach `:8000`". That reframing is what makes the `known_words` row worth a second look: it is fully attacker-controllable, and phase 2 makes it drive content selection.
  3. **No row for `session_id` (phase 3).** Task 3.1 puts a client-supplied value in the URL path (`/conversation/session/{id}/next`) and uses it as a dict key. Benign as specified — which is exactly what the row should say — but the table claims to enumerate every input, and this one is new surface introduced after the table was written.
  4. **No row for the content bank's text (phase 2).** `conversationStarters.json` is LLM-generated content that phase 2+ feeds into the TTS pipeline (and, in a session, back into the judge prompt as conversation context). The table's third row says LLM output is "never used to … inject free text into TTS" — but that is precisely what phase 2 does, just with an offline human-review step in between. The row is right about the *risk being managed* and wrong about the *mechanism*; a later reader following it literally would be misled.
- **Recommendation**: Add rows 1, 3, and 4; restate the `Source` column as "where it can originate" rather than "where it is meant to originate"; and correct row 3's wording to "LLM output reaches TTS only via the offline-generated, filtered, human-reviewed bank — never live model output at request time". The README's own closing sentence ("The judge LLM's raw output is the one row worth re-reading before any later phase extends what it's trusted to drive") is the right instinct and should point at phase 3, where session history starts feeding back into the judge prompt.

## Phase-by-Phase Review

### Phase 1 — Conversation pipeline, one fixed exchange, end to end

The phase's shape is the strongest thing in the plan: a seam task that freezes the contract, a genuinely disjoint parallel pair, and an integration proof gated on a human. The README is honest about what the phase does and doesn't deliver. The problem is that the seam task under-specifies the *browser*-facing half of the contract (CORS, audio container, non-2xx, timeouts), so four separable failure classes all converge on task 1.4 — which is the expensive place to find them, and exactly what the seam was supposed to prevent.

#### task-1.1-conversation-api-contract-and-skeleton.md: Conversation API contract + backend project skeleton
- **Status**: findings
- **Findings**: QA-1 (no CORS in a contract whose only consumer is a cross-origin browser page — the single highest-value addition to this task), QA-7 (the wire format for `reply_audio_base64` says WAV but the browser will send webm/opus; this is a contract decision and belongs here), QA-15 (`models_loaded: bool` can't support 1.4 AC1), QA-16 (pytest rootdir/pythonpath — all five backend verify lines in the plan inherit this task's config), QA-17 (`gpu` marker registration is unowned and this is the task that creates `pyproject.toml`), QA-25 (AC4 covers a missing field but not a present-but-garbage one), QA-29 (two factual slips). The two Architectural Decisions (base64-in-JSON over multipart; a written contract over generated OpenAPI) are well-argued with real rejected alternatives — no complaint there. AC2's `ac_enforcement: none` is acceptable for a doc artifact, though tying it to the phase reviewer is the weakest enforcement in the plan.

#### task-1.2-backend-pipeline.md: Backend pipeline — STT, judge, TTS
- **Status**: findings
- **Findings**: QA-4 is the substantive one — AC4 and AC5 both funnel system failures into `verdict: "fail"`, distinguishable only by English prose, which defeats the three-state rule the ACs invoke by name and poisons phase 3's tally. QA-13 (nothing here requires `conftest.py` to expose a TTS fake, yet task 3.1's entire non-GPU suite needs one), QA-25 (undecodable base64 → unhandled `500`), QA-26 (AC5's silence premise is faked, never measured against the real model, and Whisper's real silence behavior is likely to bypass the branch entirely). The GPU/non-GPU split here is the plan's best application of the convention, and the Architectural Decision explaining *why* `pipeline.py` takes models as arguments (so the non-GPU cases can substitute fakes) is exactly the right kind of rationale. The instruction to write the two failure branches "from the start, not bolted on after" is good QA-aware planning.

#### task-1.3-frontend-port-adapter-page.md: Frontend port, adapter, and page
- **Status**: findings
- **Findings**: QA-2 (the task's central reuse dependency doesn't exist on this branch), QA-3 (AC6 cannot execute in the jsdom harness as it stands), QA-5 (the `unavailable` union member covers network rejection only, not the `501`/`422`/`500` responses this very plan produces), QA-6 (no request deadline, so "never hangs" is unproven for the likeliest hang), QA-7 (blob encoded and sent with no transcoding), QA-23 (mic-denied is a first-visit-common path with no AC). AC6's framing — "proven by asserting the stub was called with a Blob, **not** by asserting on `useMicRecorder`'s internals" — is a model behavioral AC, and AC8's insistence on proving the real composition root through `renderWithApp` (rather than a bare render) is precisely the divergence CONTEXT.md warns about. Both Architectural Decisions are sound; the "unavailable is a union member, not a throw" reasoning is the plan's best-argued decision.

#### task-1.4-e2e-integration-proof.md: End-to-end integration proof
- **Status**: findings
- **Findings**: QA-14 (AC4 is unimplementable given 1.3's frozen base-URL constant and Playwright's ownership of the backend process — `page.route(...).abort()` is the fix), QA-8 (the global `webServer` array and `fullyParallel: true` both work against this task), QA-15 (AC1's failure message needs health-shape data the contract doesn't carry), QA-28 (`/conversation` vs. `/thai-script/conversation`). One further flake risk worth naming: Chromium's `--use-file-for-fake-audio-capture` **loops the file continuously** from stream start, so what `MediaRecorder` captures depends on when the click lands relative to the loop — a truncated or phase-shifted utterance reaching a real Whisper + real LLM. The verdict is greedy-decoded and therefore deterministic *given identical input*, but the input is not identical run to run. Recommend the fixtures be padded with leading/trailing silence well beyond the click-timing jitter, and that the spec assert on the verdict only after asserting the rendered transcript is non-empty — so a capture-timing failure reports as "nothing was heard" rather than as "the judge said fail". `gate: human` and the "real recorded speech, not TTS-synthesized" decision are both well-reasoned, and AC5's honesty about what no automated test can judge is right.

### Phase 2 — Personalized content, curated question bank

The central architectural call — offline generation + automated filter + human review, never live generation — is the plan's strongest decision and is properly grounded in measured spike evidence. The phase's weakness is the data contract between 2.2 (producer) and 2.3 (consumer): the README explicitly says "no seam task is needed here … 2.2's bank file format is fixed by 2.3's own read logic, which 2.2's task description states directly". It does not — 2.2 states a four-field schema that cannot answer the question 2.3 asks of it. This is the same class of problem phase 1's seam task exists to prevent, in a phase that reasoned its way out of having one.

#### task-2.1-known-vocabulary-snapshot.md: Frontend sends a known-vocabulary/grammar snapshot
- **Status**: findings
- **Findings**: QA-10 (the Architectural Decision's size argument is off by roughly 9× because it counts Thai characters rather than percent-encoded bytes; the first learner who can legitimately use this feature is already near typical request-line limits, and no AC exercises anything beyond a handful of words), QA-22 (`known_grammar_ids` is transmitted and never consumed anywhere in the plan). AC3's treatment of the empty-vocabulary case as "a real, testable state, not an assumed-never-happens one" is exactly the right instinct — the same instinct should extend to the large-snapshot end, which is where the actual failure lives. AC2's insistence on sourcing from the real `VocabularyLessonService` through a seeded harness rather than a fixture list is good.

#### task-2.2-curated-question-bank.md: Offline generation + auto-filtered question bank
- **Status**: findings
- **Findings**: QA-13 (AC2 and AC4 are marked non-GPU but need a GPU run or its output; the task's single `verify` command therefore cannot execute two of its four ACs), QA-11 (the `{id, tier, thai, english}` schema carries neither the entry's own words nor the tier's word set, so 2.3 cannot make the assertions its ACs promise), QA-21 (AC1 asserts the filter's predicate over the filter's own output — unfalsifiable), QA-24 (no minimum entries per tier, which phase 3's three-turn e2e silently depends on), QA-17 (marker registration in a second `uv` project). Note also that the existing `scripts/` precedent is pip + `requirements.txt`, not `uv` — the task's claim to follow "the existing `scripts/enrich-vocabulary.py` pattern" is about location, not tooling; worth one clarifying word so the executor doesn't hunt for a `uv` project that isn't there. Both Architectural Decisions are strong, and "tier sizes match the spike's own tested sizes, not arbitrary round numbers" is a genuinely good piece of evidence-preserving reasoning.

#### task-2.3-backend-tiered-selection.md: Backend selects from the bank by learner tier
- **Status**: findings
- **Findings**: QA-11 (three linked problems: no per-entry word list, no tier→word-set mapping available to the backend, and a "largest tier fully covered" rule that assumes the learner's known set is a frequency prefix — which real SRS graduation order does not produce, making the normal case fall through to the empty-set branch), QA-12 (the Architectural Decision is an unresolved placeholder and AC3 has no expected value), QA-9 (AC4's two-fixture e2e needs a seeding mechanism no task builds). One further cross-project concern: AC1 asserts against "the REAL `conversationStarters.json` task 2.2 produced", which lives under `src/domain/conversation/data/` — the backend is a separate `uv` project rooted at `backend/`, and nothing in the task says how it locates or loads a file in the frontend tree, nor what happens when that file is absent (a clean checkout, or before 2.2 has run). Worth one explicit sentence, since it also determines whether `backend/tests` can run standalone. The deterministic-selection decision (hash over known-words rather than `random.choice`, so a refresh doesn't reshuffle) is well-reasoned and correctly defers variety to phase 3.

### Phase 3 — Multi-turn sessions + feature gating

The phase correctly identifies itself as the one that makes the feature what was asked for, and the 3.1/3.2 independence argument holds up (a locked screen genuinely never calls the backend). The gating design — a pure function mirroring `meetsPrerequisites`, enforced at both the Dashboard and the page — is the right shape, and the "duplicated at two call sites on purpose" decision is well-argued against this app's actual lack of route-guard infrastructure. The session work is where the QA gaps concentrate: one vacuous AC, one AC naming a mechanism that doesn't exist, and no coverage of the concurrency the auto-advance UI introduces.

#### task-3.1-backend-session-state.md: Backend session state + a continue endpoint
- **Status**: findings
- **Findings**: QA-18 (AC4 cannot fail and proves nothing about the non-persistence property it names), QA-19 ("expired" session ids with no expiry mechanism), QA-20 (select-then-record is not atomic, and 3.3 drives `/next` from an automatic advance under `StrictMode` — two in-flight calls can hand out the same entry, which AC1 forbids), QA-13 (every AC is marked non-GPU but AC1 returns `question_audio_base64`, requiring a TTS fake task 1.2 is not obliged to provide). AC2's treatment of exhaustion as a named response field is right, and the Architectural Decision explaining why — "an empty `200` would be indistinguishable from 'something went wrong selecting an entry'" — is a clean application of the plan's three-state rule to a new surface. The opaque-session-id decision is correct and correctly reasoned (content-keyed ids would collide two learners with identical snapshots).
